1. PURPOSE AND CURRENT GOAL
The user is developing custom DayZ weapon-raised/aiming lean poses. They want natural torso, head, arms, elbows, hands, weapon and leg placement with stable support-hand contact, responsive native-style aiming, and smooth transitions without delaying weapon raising or shooting.

A newer stationary lean looks better than the old walking lean. Moving between stationary lean and walking lean visibly changes the torso, arms, head and gun. In particular, stationary left lean places the weapon almost on the left shoulder, whereas walking left lean places it on the right shoulder. The immediate goal is to tune walking lean against the approved stationary pose using two simultaneous NPC references, then apply the approved walking settings to the player.

The user wants local editing and builds instead of repeatedly waiting for remotely prepared ZIP tests. They also want eventual autonomous game testing, but desktop/game-control access has NOT been established.

5. COORDINATES, POSE AND CONTROL PREFERENCES
Model position axes:
X = character's own right; positive X moves right.
Y = up; negative Y lowers the weapon/body part.
Z = forward; positive Z moves forward.
UI position values are centimetres. Rotation controls are degrees; actual native sign depends on the graph's Model ProcTransform convention.

The user repeatedly corrected confusion between lateral X, vertical Y and depth Z. Prior forward requests meant along the weapon-facing direction, not arbitrary world axes.

The user requires the same custom lean poses in first and third person, including raised/ADS views. Camera-specific custom lean poses are not desired unless explicitly requested.

Useful retained controls:
- F6: weapon/arms/head editor.
- F7: body editor.
- Ctrl+F1: native/custom lean comparator, starts custom; no save/reset.
- Ctrl+F8: arm-drop comparison.
- X: diagnostic freeze, replacing Alt-based freezing.
- RMB held in editor: navigation.

Older L/colon recording/replay and female NPC features were removed before the current preview system. They are not current controls.

The current third-person inspection camera sits at least about 4 metres back in open space and has a lowered pivot for full-body inspection. Native collision can move it closer near walls. First-person/ADS camera was not changed by that inspection-camera addition.

7. RELEVANT DEVELOPMENT HISTORY
Early versions repeatedly addressed camera/arm speed mismatch, support-hand slipping during view movement, delayed raising/lean transitions, transient weapon/arm flashes in front of the camera, and unwanted native lean tilt mixing with custom poses. Several versions were rolled back after regressions; old version numbers alone are not evidence that an experiment worked.

The user found v89 stable, then achieved effective lowering of weapon/arms on the right side around v95. Later experiments adjusted left-side elbows, shoulder alignment, gun offsets and support grip. Historical values were superseded by the latest approved preset.

Panacea weapons appeared equipped but raised fists or failed switching/handling while the native NPC AK74 worked. Panacea was abandoned in favour of AJs Weapons. An AJs dependency error required JM_CF_Scripts. External weapon mods were later removed from the current test loadout. Current code should not be assumed to need AJs or Community Framework.

Live editing evolved through v144-v153:
- F6 weapon panel, then arm/head page, both-side values and muzzle aiming controls.
- F7 full body editing.
- RMB navigation with panels open.
- Unified combined save so weapon/arms/head and body changes are preserved together rather than only body changes.

V160 restored visible rightward body displacement after the new right pose appeared almost stationary despite camera motion. Its pelvis correction is approximately +32.3 cm relative to a displaced old baseline; it is not a request for 32.3 cm total lean travel. The latest user preset was tuned on this base. Left leg stance changed; the user explicitly prioritised actual rightward body movement and planned to retune the pose afterward.

NPC/player apparent height and head differences were investigated. Initial head bone heights were both about 1.61069 m, with no demonstrated scale multiplier. The NPC's real native stance/raised state differed from the player's because the demo uses graph canary forcing. V162 attempted native raised stance forcing and failed: the NPC stayed in default lowered lean. V163 restored the working v161 demo approach. The apparent height difference was not conclusively resolved; blind NPC scaling was not supported by evidence.

V164 compacted graph transforms to reduce graph depth but did not eliminate the native left-walk-stop crash.

V165 addressed repeated base-pose evaluation in four fractional left-side correction layers. This is a crash mitigation, not a confirmed native fix.

V166-v168 moved aim after custom body/arm/head edits, enabled native arm-chain solves off-centre, and added native aim pitch/yaw to the final weapon target. The user confirmed grip improved in v167 but reported delayed movement and missing weapon pitch. V168 corrected the omitted final native angle input. Comprehensive native confirmation was not subsequently established.

V169 added Ctrl+F1 native/custom comparison.
V170 removed the old separate first-person crouch-style presentation so both views share custom poses.
V171 only widened the third-person camera; it did not change feet or animation.

V172 attempted to keep the current stationary upper body while walking through one-shot, cached native pose retargeting. It requires standing and walking references per side/direction/gait/ADS mode, never per-frame corrected-output feedback. The user reported the walking-left weapon still sat on a different shoulder. V173 responds with isolated direct walking tuning rather than claiming v172 solved that discrepancy.

8. CRASH AND PERFORMANCE RISKS
A repeat native crash occurred while leaning left and walking left, then stopping. Earlier descriptions also called it an ADS-exit or freeze crash.

The v164 minidump showed the same native fault as v163. Exception-context analysis found an internal signed-16-bit boundary at 32,769 entries and an out-of-bounds indexed write. Exact internal native function names were unavailable.

Four old fractional LEFT layers could repeatedly evaluate the full underlying base pose, up to 16 times together during transitions:
- ML104_LeftElbowDirections
- ML118_ContactHoldOnly
- ML130_StandingLeftOnly
- ML133_StandingLeftElbow

V165 changed their routing to binary optimised selection with weighted correction transforms. Full endpoints were retained, but fractional interpolation changed. V173 preserves those gates. A later normal session exit does not prove the exact old crash reproduction is fixed.

A large FPS drop on every NPC left/right switch was previously reported. No current native performance benchmark proves that all transition costs are eliminated. Per-frame pose-feedback loops previously caused flipped/disappearing hands and are not the current reference strategy.

The log collector includes the newest minidump up to 24 MiB. Larger dumps are left in place with their location reported. No dumps are sent automatically.

11. KNOWN ENFORCE/NATIVE API CONSTRAINTS FROM PAST FAILURES
- Bone used as a field name collided with a native type; current schema uses BoneName.
- local is reserved.
- Large field-access array initialisers triggered Formula too complex; individual Insert statements solved those failures.
- Nested arithmetic/getter expressions sometimes produced Broken expression; temporary variables were required.
- Vector/scalar division was unsupported in the used context; reciprocal multiplication was used.
- Graph float binding ID 0 is valid; missing bone ID is -1, while other negative bone IDs can be valid.
- AnimSetFloat graph writes belong inside CommandHandler after native processing; UI changes cached settings.
- GetCommandModifier_Weapons is the actual API used, not GetCommand_Weapons.
- No verified public AnimGetFloat/GetVarFloat getter was available.
- HumanInputController.GetMovement returns normalized local direction.
- Model ProcTransform native rotation signs are negative right-handed XYZ in the implemented math.
- Position/rotation values are not equivalent to safe IK targets: independent F7 limb changes can alter foot plant or grip.
